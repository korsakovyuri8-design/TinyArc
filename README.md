# TinyArc Cloud Bureau

AI-native архитектурное бюро. Отдельный венчур в составе TinyArc Group.

**Манифест:** *The bureau that ends the bureau.*

Мы не помогаем локальному архитектурному бюро — мы занимаем его место. Алгоритм
отбирает специалистов по фактам, собирает под проект временную команду и ведёт
её до пакета документации. Здания до пяти этажей в зонах лёгкого регулирования:
Черногория, Сербия, Греция.

Канонический документ проекта — [`docs/concept.md`](docs/concept.md). Ссылки
вида «п.9» в коде и в интерфейсе указывают на его разделы.

## Запуск

```bash
npm install
cp .env.example .env
npm run demo       # генерация клиента + схема + сид + сервер на localhost:3000
```

Отдельно, если нужно по частям: `npm run setup`, затем `npm run dev`.

```bash
npm test           # модульные тесты движка и обвязки
npm run typecheck
npm run build
npm run e2e        # сквозные пути: клиент, приём базы, вёрстка, правка профиля,
                   # разговор заказчика с бюро.
                   # Нужен запущенный сервер и BUREAU_OPS_PASSWORD в окружении
```

| `/ops/pool/[id]` | Профиль специалиста: правка полей отбора бюро |
| `/work/profile/complete` | Дозаполнение профиля по приглашению |

Ключи после `npm run demo`:

- клиент — `seed-brief-tivat`, `seed-brief-novisad`, `seed-brief-athens`,
  `seed-brief-rejected` (последний показывает отказ по продуктовой границе);
- специалист — `seed-key-01` … `seed-key-72`, входят только подтверждённые;
  на первом проекте один тикет намеренно оставлен в конфликте — арбитраж видно
  в `/ops`;
- бюро — `/ops`, пароль из `BUREAU_OPS_PASSWORD` (по умолчанию `bureau-ops`).

Вход — `/enter`, одной формой на обе стороны: ключ сам знает, чей он.

## Как устроен код

```
src/engine/     движок: ничего не знает про базу и про React
  taxonomy.ts   двенадцать измерений, специализации, сценарная матрица ролей
  filter.ts     жёсткие гейты, технологический шлюз
  score.ts      Quality × Availability, шкала в сотне
  assemble.ts   сборка Tiny Team
  relay.ts      атомарные тикеты, граф зависимостей, стадийные гейты
  direction.ts  направления проекта: что применимо к этому участку
  collaboration.ts  сработанность пар: влияет на порядок вариантов, не на гейты
  metrics.ts    SLA, First Time Right, Response Time, Revision Rate
  pm.ts         цифровой менеджер: сигналы по срокам, хендоффам, конфликтам
  readiness.ts  готовность пула: что можем взять и кого не хватает
  validate.ts   продуктовая граница проекта

src/lib/        мост между базой и движком, сессии, формы, подписи
src/app/        интерфейс: путь клиента, путь специалиста, панель бюро
```

Разделение жёсткое: всё, что решает, кто попадёт в команду, живёт в `src/engine`
и покрыто модульными тестами. Страницы читают и показывают, но не решают.

## Четыре вещи, которые ломать нельзя

Они зафиксированы концептом и держатся структурой кода, а не договорённостью.

1. **Команду собирает движок.** В схеме нет поля, которым оператор мог бы
   назначить специалиста в команду. Слот создаётся только прогоном и хранит
   разбор балла и требование роли, по которым создан (п.7).
2. **Blind Relay.** Модели личного сообщения между специалистами не существует.
   Единственный носитель коммуникации — комментарий, привязанный к тикету.
   Спор решает арбитр — бюро (п.11).
3. **Метрики математические.** Поля «оценка специалиста» нет ни у клиента, ни у
   бюро. Качество считается из времён тикетов (п.12).
4. **AI — менеджер, не исполнитель.** Цифровой PM следит за сроками и
   хендоффами и сигналит. Чертежи делают люди (п.12а).
5. **Направление — не часть комплекта.** Оно хранится отдельной моделью, а не
   среди артефактов проекта: артефакты передаются по графу и складываются в
   пакет документации, направление — нет и не должно (п.7а).
6. **Клиент не получает контактов команды.** Выборка специалиста для кабинета
   задана поимённо (`VISIBLE_SPECIALIST`), а не `include: { specialist: true }`:
   полная строка несёт почту и ключ доступа. Сквозной тест это проверяет (п.13).

## Секреты

В боевом окружении восемь переменных обязательны, и без любой из них приложение
**не стартует** — `scripts/preflight.ts` останавливает запуск на выкладке, а не
поднимает сайт, отдающий 500 первому же посетителю:

- `BUREAU_OPS_PASSWORD` — панель бюро;
- `BUREAU_SESSION_SECRET` — подпись cookie сессии;
- `BUREAU_LEGAL_NAME`, `BUREAU_LEGAL_REGISTRATION`, `BUREAU_LEGAL_ADDRESS`,
  `BUREAU_LEGAL_EMAIL` — реквизиты юрлица. Оферта без наименования и
  регистрационного номера — не договор, а политика обработки без адреса для
  обращений не даёт человеку сделать то, на что у него есть право;
- `BUREAU_STORAGE=s3` вместе с `BUREAU_S3_ENDPOINT`, `BUREAU_S3_BUCKET`,
  `BUREAU_S3_ACCESS_KEY_ID`, `BUREAU_S3_SECRET_ACCESS_KEY`. Диск контейнера в
  бою запрещён явно: он живёт до следующей выкладки, а отдавать заказчику
  комплект придётся сильно позже неё (п.13).

Всё это `render.yaml` спрашивает при развёртывании, и что он спрашивает ровно
то, что требует preflight, сторожит `src/lib/render.test.ts`: он собирает
окружение из блюпринта и прогоняет через тот же preflight, что стоит на
боевом запуске. Один раз файл уже разошёлся с проверкой — блюпринт задавал два
секрета из восьми, и выкладка по нему упала бы на старте.

`BUREAU_PUBLIC_URL` секретом не является и обязательной не стала: без неё берётся
канонический адрес продукта. Заданная, она обязана быть https вне localhost —
по этому адресу ходят ключи доступа.

Значения по умолчанию существуют только для локальной машины и напечатаны в
этом файле. Напечатанный пароль паролем не является: поэтому в бою подстановки
нет, есть отказ стартовать.

Помощники бюро задаются `BUREAU_ASSIST`: `stub` собирает черновик по шаблону из
фактов проекта, `anthropic` — моделью. В обоих случаях результат черновик,
который правит человек; отбор, приёмку и проектные разделы помощник не трогает.

Изображения направлений задаются `BUREAU_IMAGES`: `stub` рисует схему объёма
без сети и без ключа, `openai` генерирует изображение. Адаптер провайдера на
живом ключе не проверялся — режим по умолчанию `stub`, поэтому непроверенный
код не включается сам собой.

Почта задаётся `BUREAU_MAIL`: `stub` пишет письмо в лог и никуда не шлёт,
`resend` отправляет по-настоящему. Неизвестное значение роняет приложение, а не
откатывается на заглушку молча. В режиме `stub` ключ доступа показывается
человеку на экране, поэтому доступ не теряется — просто выдаётся вживую.

## Выкладка

```bash
# стенд целиком: приложение, Postgres и хранилище файлов
BUREAU_OPS_PASSWORD=… BUREAU_SESSION_SECRET=… POSTGRES_PASSWORD=…   docker compose up --build

# то же, но с синтетическим пулом
docker compose -f docker-compose.yml -f docker-compose.demo.yml up --build
```

Хранилище у стенда настоящее (MinIO), а не диск контейнера, и это не
щепетильность: образ собран с `NODE_ENV=production`, а в бою диск контейнера
запрещён явно — стенд с ним просто не стартовал бы. Заодно здесь работает тот
самый код, который поедет в бой: MinIO говорит на том же протоколе, что R2 и
AWS. Реквизиты юрлица у стенда свои и ненастоящие; для пилотного стенда
передайте настоящие теми же переменными.

На Render: New → Blueprint → этот репозиторий. `render.yaml` поднимет Postgres и
приложение и спросит значения, помеченные в нём `sync: false` — что именно и
что отвечать, написано в самом файле рядом с каждой строкой. По умолчанию там
стоит демонстрационный запуск с пулом; для боевого стенда замените
`dockerCommand` на `sh ./scripts/start.sh`, и база останется пустой.

Живость — `/api/health`. Наружу уходит только «да» или «нет».

### Порядок первой выкладки

1. **Хранилище.** Завести S3-совместимый бакет — подходит любой, Cloudflare R2
   дешевле прочих и не берёт за исходящий трафик. Из панели R2 нужны четыре
   значения: адрес эндпоинта, имя бакета и пара ключей.
2. **Реквизиты.** Наименование, регистрационный номер, юридический адрес и
   адрес для правовых обращений. Без них оферта и политика неполны, и
   preflight это не пропустит.
3. **Blueprint.** New → Blueprint, ответить на вопросы Render.
4. **DNS.** Запись CNAME по таблице ниже; сертификат Render выпустит сам.
5. **План базы.** У бесплатного плана Postgres нет резервных копий. Для пилота
   с живыми заказчиками это единственное место, где деньги стоит потратить
   сразу: потерянная база — это потерянные проекты людей, а не наши.
6. **Почта.** Пока `BUREAU_MAIL=stub`, письма никуда не уходят, и это видно из
   конфигурации. Кого позвать руками — список в панели на `/ops/letters`.
   Включается почта двумя значениями: `BUREAU_MAIL=resend`, `RESEND_API_KEY`,
   `BUREAU_MAIL_FROM`.
7. **Юрист.** Три документа — оферта, условия для специалиста, политика
   обработки — написаны и связаны согласием, но юристом не смотрены. Это
   единственный пункт, который не закрывается ни кодом, ни настройкой.

## Адрес

Продукт живёт на **tinyarc.korsakovgroup.com** — поддомене домена группы. Адрес
зашит в `src/lib/site.ts`: из него собираются канонические ссылки страниц,
карта сайта и ссылка на вход в письме с ключом доступа. Переопределяется
переменной `BUREAU_PUBLIC_URL` — она нужна превью-стенду и локальной проверке
почты, а не бою.

Одна запись в DNS, без которой ничего из этого не работает. Домен обслуживается
Namecheap BasicDNS (`dns1/dns2.registrar-servers.com`), поддомена `tinyarc` в
зоне пока нет:

| Тип | Host | Value | TTL |
| --- | --- | --- | --- |
| CNAME | `tinyarc` | значение со вкладки Render → Settings → Custom Domains, вида `tinyarc-bureau.onrender.com` | Automatic |

Namecheap → Domain List → korsakovgroup.com → Advanced DNS → Add New Record.
Значение берётся из Render, а не из этой таблицы: Render показывает точный хост
после того, как домен добавлен сервису. Сертификат Render выпустит сам, когда
запись разойдётся по DNS — обычно минуты, изредка до часа.

Корень `korsakovgroup.com` и `www` эта запись не трогает: они как стояли на
парковочной странице регистратора, так и останутся. Поддомен живёт отдельно.

## База

Разработка — SQLite, бой — Postgres. Схема одна, второй файл генерируется:

```bash
npm run db:schema          # записать prisma/schema.postgres.prisma
npm run db:schema:check    # проверить, что не отстал
```

Провайдер выбирает не человек, а `DATABASE_URL`. Молчаливого отката на SQLite
нет: «кажется, боевая база» — худшее из состояний.

Миграции существуют только под Postgres — боевая база она. Локальная разработка
идёт на SQLite через `npm run db:push`, без миграций.

Если из схемы убрали колонку, `npm run setup` на уже существующей локальной базе
остановится: Prisma не станет терять данные без разрешения. Локальная база —
синтетический стенд, который сид и так чистит при каждом запуске, поэтому проще
всего пересоздать её целиком:

```bash
rm -f bureau.db && npm run setup
```

**Применённую миграцию менять нельзя.** Prisma хранит её контрольную сумму и в
бою отказывается стартовать при расхождении, а локально этого не видно вовсе —
разработка идёт без миграций. Изменение схемы оформляется новой:

```bash
npx prisma migrate diff \
  --from-schema <схема до изменения> \
  --to-schema prisma/schema.postgres.prisma --script \
  > prisma/migrations/000N_имя/migration.sql
```

Суммы всех миграций зафиксированы тестом (`src/lib/migrations.test.ts`) —
миграция неприкосновенна с момента коммита, а не с момента выкладки. Новая
добавляется в тест вместе с файлом.

## Статус

Прототип. Платящих клиентов нет (`docs/concept.md`, п.25). Репозиторий закрывает
кликабельный прототип, лендинг и выкладку; первый пилотный клиент кодом не
закрывается.

Что осознанно не сделано: аутентификация — это ключ доступа, а не пароль с
восстановлением; ограничение частоты считается в памяти процесса и при
нескольких инстансах у каждого своё; артефакты хендоффа — ссылки, а не файлы.
Каждое из трёх заменяется локально и помечено в коде.
